# Thinker 异步机制与线程边界（面试速查）

> 源码版本：v0.13.0，行号于 2026-11-14 核对。本文只解释机制，不涉及代码改动。

## 一句话结论

**一个事件循环跑在主线程；三个 daemon 线程通过 `queue.Queue` / `threading.Event` 与它通信，不共享事件循环；流式阶段主线程每 50ms 从阻塞里醒一次查 Esc，那段时间事件循环本身是停的。**

---

## 1. 只有一个事件循环，在主线程上

`main.py:240` 的 `asyncio.run(main(resume_path))` 做三件事：建一个事件循环、把 `main()` 作为第一个任务跑起来、跑完收尾。这个循环**就跑在启动进程的那个线程里**，所有 `async def` / `await` 都是它从就绪队列取出来执行的回调，彼此靠「遇到 `await` 主动让出」切换。

```python
async def main(resume_path=None):
    conversation = Conversation()
    try:
        await conversation.start_conversation(resume_path)
    finally:
        await conversation.shutdown()      # Ctrl+C 也会走这里
```

`start_conversation → _recursive_message_handling → _run_one_iteration` 全在这条链上。**没有第二个事件循环，也没有第二个线程在跑 asyncio。**

## 2. 三个 daemon 线程：何时起、何时停

| 线程 | 创建位置 | 触发时机 | 怎么停 |
|---|---|---|---|
| **EscWatcher** | `esc_watcher.py:100`<br>`threading.Thread(..., daemon=True, name="esc-watcher")` | 每轮 `start_stream_display()` 之后，`esc.reset()` → `esc.start()`（`conversation.py:1045-1047`） | `finally: esc.stop()` → `_stop.set()` + `join(timeout=1.0)`；读到 `0x1b` 后线程自己 `return` |
| **流式读泵** | `stream_pump.py:96`<br>`threading.Thread(..., name="thinker-stream-pump", daemon=True)` | 每次进入 `iter_stream_with_esc(iterator, esc)` 且 `esc is not None` | 生成器被关闭时 `finally: stop_pump.set()`；泵线程**下一块数据到达后**才看到标志退出 |
| **spinner** | `display_manager.py:493`<br>`threading.Thread(..., daemon=True)` | 每轮 `start_stream_display()`，条件 `_is_tty()` 且未设 `THINKER_NO_SPINNER=1`；延迟 200ms 才开始画 | `_stop_spinner()` → `_spinner_stop.set()` + `join(timeout=1.0)`，然后擦行、恢复光标 |

三个都是 `daemon=True`：主流程异常退出时不会把进程拖住。代价是**无法主动取消**——泵线程可能仍阻塞在 `next(iterator)` 这个网络读上，`stop_pump` 只在它下一次循环开头被检查，所以会滞后一块数据才退出。

**降级条件**：`EscWatcher.available` 要求 Windows + `sys.stdin.isatty()`。不满足时 `start()` 静默返回，`esc is not None` 但 `triggered` 永远为 False，`iter_stream_with_esc` 仍走泵 + 队列，只是 Esc 功能不存在；只有 `esc is None`（明确不支持打断）才走 `yield from iterator` 直通。`THINKER_PLAIN_INPUT=1` 只关输入行自管编辑，不影响这个监听。

轮询节奏：`EscWatcher` 50ms（`esc_watcher.py:122`）、主线程取队列 50ms（`stream_pump.py:36`）、spinner 100ms（`display_manager.py:550`）。

## 3. 按 Esc 那一瞬间，四条执行流各在干什么

1. **EscWatcher 线程**：`_loop` 每 50ms 查 `msvcrt.kbhit()`；读到 `0x1b` → `_pressed.set()` → 直接 `return`（线程结束）。其它键被 `getch()` 消费后丢弃。
2. **主线程**：此刻大概率阻塞在 `chunk_queue.get(timeout=0.05)`；`get` 超时醒来后，`while True` 的**第一句**就是 `if esc.triggered: raise StreamInterrupted()`——不依赖有没有数据到达。这就是「模型思考、一个 chunk 都没有时也能打断」的全部秘密。
3. **泵线程**：完全不知道发生了什么，仍在 `for item in iterator` 里；它可能继续 `put` 一两块，直到看到 `stop_pump`（生成器因异常被关闭 → `finally` 设标志）。队列里剩下的数据没人再消费，随队列对象一起回收。
4. **spinner 线程**：照常每 100ms 写 `\r + 帧 + 空格补齐`；直到主线程走到 `stop_stream_display(show_done=False)` → `_stop_spinner()` 才被 `join` 停掉。

> 关于「Esc 响应 ≤50ms」的准确口径：代码是**两级 50ms**——EscWatcher 最多 50ms 发现按键，主线程最多再 50ms 醒来看标志，最坏叠加约 100ms；实际两级错开、且吐字时 `get` 立刻返回会检查得更频繁，体感几十毫秒。被追问时按这个答。

## 4. 跨线程通信原语，以及为什么不能用 asyncio 那套

| 数据 | 原语 | 谁写 → 谁读 |
|---|---|---|
| 流式 chunk | `queue.Queue`，三种消息 `("chunk", item)` / `("end", None)` / `("error", exc)` | 泵线程写 → 主线程 `get` |
| 有没有按 Esc | `threading.Event _pressed` | EscWatcher `set` → 主线程 `triggered` 读 |
| 停止信号 | `_stop` / `stop_pump` / `_spinner_stop`，三个 `threading.Event` | 主线程设 → 各自线程读 |

`queue.Queue` 内部带锁，`threading.Event.set()` 是原子的，跨线程安全。**`asyncio.Queue` / `asyncio.Event` 不行**：它们绑定创建时的那个 loop 且不是线程安全的，从别的线程直接 `set()` 不会正确唤醒等待者（真要用得 `loop.call_soon_threadsafe(...)`）。项目里两种 Event 分得很干净——只有 MCP 客户端的 `_ready` / `_shutdown` 是 `asyncio.Event`，因为那两个只在协程之间用。

---

## 5. 最反直觉的一点：那 50ms 里事件循环其实「停了」

`for chunk in iter_stream_with_esc(...)` 是个**同步生成器**，虽然写在 `async def _run_one_iteration` 里，但 `chunk_queue.get(timeout=0.05)` 是一次普通的**阻塞调用**，不是 `await`。所以：

- 这 50ms 内**事件循环线程被占住**，循环里其它协程（例如后台注册 MCP 的 `create_task`）也跑不了；
- 三个后台线程照常工作，因为 `Queue.get` / `Event.wait` 等待时会**释放 GIL**，OS 会调度其它线程；
- 界面看着「还活着」，靠的是那三个独立线程，**不是**靠事件循环。

准确说法：主线程和事件循环是同一个线程，但流式阶段它每 50ms 被阻塞一次，没在调度协程。这是刻意取舍——`openai` 用的是同步 SDK、生成器没有 `await` 点，换 `AsyncOpenAI` 是另一个量级的改动；现在用「线程搬数据 + 主线程轮询」换来 Esc 随时可打断。

---

## 6. 别把「不在事件循环上」混成一类

| 类别 | 在哪 | 与主链怎么同步 |
|---|---|---|
| 线程池（executor）`run_in_executor` / `to_thread` | 不在事件循环上 | 主链 `await` 一个 Future，**有明确同步点** |
| `create_task` 的任务（MCP 注册、`AsyncExitStack` 总任务） | **在**事件循环上 | 用 `asyncio.Event`，只在协程之间通信 |
| 三个 daemon 线程 | 完全在 asyncio 体系之外 | 只靠线程安全原语交换数据，**没有 `await` 关系** |

---

## 7. 两个线程安全细节

- `_reasoning_chars`（思考字数）是主线程写、spinner 线程每 100ms 读，故意**没加锁**——注释写明「最坏读到上一帧旧值，对一个心跳计数器够用，加锁反而会在热路径引入争用」。真正要求准确的标志（按没按 Esc、该不该停）全用了 `Event`。
- `EscWatcher.start()` 有 `is_alive()` 判重，防止两个线程同时 `getch()` 抢字符；`stop()` 必须 `join`，否则下一轮新线程和旧线程会抢键盘。

---

## 面试速答

> 一个事件循环跑在主线程；三个 daemon 线程通过 `queue.Queue` / `threading.Event` 与它通信，不共享事件循环；流式阶段主线程每 50ms 从阻塞里醒一次查 Esc，那段时间事件循环本身是停的。

配套可追问的三个边界：**没有取消 HTTP 请求**（服务端照常生成、照常计费，客户端只是不再读）；**思考阶段按 Esc 历史里不留痕迹**（`full_content` 为空，不写 `[用户中断]`）；**并发不等于并行**（管家全是单例，一次只能跑一个子 agent）。
