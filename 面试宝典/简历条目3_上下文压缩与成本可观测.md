# 简历条目三：上下文压缩与成本可观测 —— 由来、流程、名词、验证

> 简历原文：**四阈值五档按占用比例只触发对应档、档间互斥不叠加（剪中间 / 折叠工具结果 / 只读投影 / 模型摘要），15 轮 151 条场景从 95.0% 压至 6.7%，技能清单常驻 1,958 字符（约 979 token/轮）；system 与末尾双缓存断点按接口自动判定；相邻只读调用并发，结果按申请顺序写回。**

---

## 一、由来背景

### 1.1 为什么压缩要分五档
上下文占用率（已用 token / 窗口上限）到了临界点，模型质量下降、请求变贵，直到彻底装不下。但"一刀切全部摘要"有两个问题：一是**贵**（调一次模型摘要本身花钱花时间）；二是**伤精度**（早期明明剪一剪就够）。所以按占用率把治理手段从轻到重排成档位——占用刚过线就只做最便宜的动作，越往后手段越重（`src/core/history/history_manager.py`）：

| 档 | 触发区间（默认值） | 手段 | 是否调模型 |
|---|---|---|---|
| L2 Snip | [0.80, 0.85) | 剪中间（删旧轮次的中段） | 否 |
| L3 Microcompact | [0.85, 0.90) | 旧工具结果二次瘦身（折叠） | 否 |
| L4 Context Collapse | [0.90, 0.95) | 只读投影 | 否 |
| L5 Compact | ≥0.95 | 模型摘要，按边界一次压完 | **是** |

用户 `.env` 把四阈值实际设为 **0.70 / 0.75 / 0.85 / 0.90**（更早触发）。**档间互斥不叠加**：当前占用落在哪个区间，就只执行那一档的手段——刚到 0.80 就做剪中间，不会同时跑摘要；这样每次治理的动作最小、成本最低。

### 1.2 为什么技能清单要算"常驻成本"
技能清单 1,958 字符随系统提示词**每一轮都发**。这是成本可观测的一部分：不是"隐性膨胀"，而是显式算出来的一笔固定开销——约 979 token/轮（按 2 字符/token 的粗估口径；若按项目文档 3 字符/token 则约 650）。它换来的是模型随时知道自己有哪些技能可用。

### 1.3 为什么做双缓存断点
主流模型接口有 **prompt caching**：前缀完全相同的请求，命中缓存的部分按大幅折扣计费、且更快。但缓存命中要求**前缀逐字节一致**——任何变化都会"断缓存"。对话消息每轮都在追加，所以断点要打在两个位置：**system 提示词末尾**（整段不变，永远命中）和**当前消息列表末尾**（下一轮新增消息后，旧前缀仍可命中）。不同接口的缓存机制不同（有的显式打标、有的自动前缀匹配），所以"按接口自动判定"断点打法。

### 1.4 为什么只有"相邻只读"才能并发
工具调用有先后依赖风险：第一条命令 `git checkout` 会改变工作区，第二条 `git status` 的结果就依赖它。只有**相邻的、都是只读的**调用才保证互不影响，可以安全并行；一旦有写操作或顺序敏感，必须串行。这是在"省时间"和"正确性"之间画的一条保守线。

## 二、完整流程步骤

### 2.1 五档压缩的触发与执行
1. 每轮工具结果回填后，`update_token_usage` 统计当前占用率（粗估：字符数 ÷ 每字符 token 系数）；
2. 用占用率对四阈值做**区间映射**，得到唯一命中的档位（互斥，不叠加）；
3. 命中 L2：把较早轮次的中间消息剪掉，保留首尾关键锚点（用户原始诉求、最近几轮）；
4. 命中 L3：对更早的**旧工具结果**二次瘦身——大段输出折叠成一行摘要占位；
5. 命中 L4：**只读投影**——把只读类调用的完整结果投影成精简版（结论 + 关键路径）；
6. 命中 L5：调模型做摘要，且**按消息边界一次压完**（`_compress_by_boundary`），不会把半句话压掉；
7. 全程消息历史结构 `messages_history = [[]]` 不破坏，翻页语义保留。

### 2.2 双缓存断点
1. 构造请求时，先放**不变前缀**：system 提示词（含技能清单等）；
2. 按当前接口能力自动判定：支持显式缓存断点的接口，在 system 末尾和消息列表末尾各打一个断点；自动前缀缓存的接口则保证前缀逐字节稳定（技能清单 `available_block()` 的输出稳定性正是为此设计的——不是巧合而是依赖）；
3. 下一轮请求时，旧前缀命中缓存 → 计费折扣 + 更快首 token。

### 2.3 相邻只读并发
1. `_handle_tool_calls` 拿到本轮工具调用列表后扫描：找出**相邻且都属只读白名单**的连续段；
2. 该段用 asyncio 并发执行（各自独立 await），**有写操作或顺序敏感的段保持原序串行**；
3. 结果**按申请顺序写回**消息历史——即使第 2 个先完成，写入位置仍按模型申请时的顺序，保证历史与模型的预期一一对应；
4. 实测口径：0.3s / 0.31s 这组数字来自 `test/test_parallel_tools.py` 的**离线测试**——用 sleep(0.3) 模拟工具耗时，不真调模型。

## 三、专业名词解释

| 名词 | 确切含义 |
|---|---|
| **上下文占用率** | 已用 token ÷ 模型上下文窗口上限，压缩机制的触发依据。 |
| **四阈值五档** | 四条触发线把占用率切成区间，每区间对应一种治理手段（外加不触发的正常档，合称五档）。 |
| **档间互斥** | 每次只执行当前区间对应的那一档手段，不把几档手段叠着做。 |
| **Snip（剪中间）** | 删除旧轮次中段消息、保留首尾锚点的压缩方式，纯本地操作。 |
| **Microcompact（折叠工具结果）** | 把早期的大段工具输出折叠成一行占位摘要，不调模型。 |
| **只读投影** | 把只读调用的完整结果替换为"结论+关键信息"的精简投影。 |
| **模型摘要（Compact）** | 调一次 LLM 把大段历史总结成摘要，最重但压缩比最高的手段。 |
| **消息边界** | 以完整消息为单位压缩，绝不切断半条消息，保证语义完整。 |
| **prompt caching（提示词缓存）** | 服务端对完全相同的前缀做缓存，命中部分按折扣计费。 |
| **缓存断点（cache breakpoint）** | 显式标记"到这里为止的前缀可被缓存"的位置；打在 system 末尾和消息列表末尾两处。 |
| **token** | 模型计费与计长的最小单位；本项目粗估口径 2 字符/token（文档口径 3 字符/token）。 |
| **只读白名单** | 判定为"不改变任何状态"的工具集合，是并发安全的前提。 |
| **申请顺序写回** | 并发执行但结果按模型申请时的顺序入历史，保持因果一致。 |

## 四、测试验证方法

1. **压缩档位测试（`test/test_compress_boundary.py`）**：纯离线。构造 15 轮、151 条消息的模拟场景，逐档喂入不同的占用率，断言：只触发对应档、档间不叠加、每档压缩后的结构与边界完整。实测该场景从 **95.0% 压至 6.7%**。
2. **边界压缩测试**：构造"半句话"式消息序列，验证 `_compress_by_boundary` 从不产生截断消息。
3. **并发测试（`test/test_parallel_tools.py`）**：离线，用 sleep 模拟延时。两个相邻只读调用并发执行，总耗时 ≈ 单个耗时（0.3s，而不是串行的 0.6s）；再构造"只读+写"相邻的组合，断言**不并发**（保持串行）。这组 0.3s/0.31s 是模拟数据，面试要说明是离线测试口径。
4. **写回顺序断言**：并发段完成后逐条比对消息历史中工具结果的顺序与模型申请顺序一致。
5. **成本可观测验证**：token 用量统计每轮更新；技能清单 1,958 字符是在真实会话里从 `available_block()` 的输出长度量出来的，换算 token 是估算口径（979，按 2 字符/token）。

## 五、面试问答备查

- **Q：95.0% → 6.7% 是什么场景？** A：15 轮 151 条消息的离线模拟场景（test_compress_boundary.py），不是线上真实会话。
- **Q：为什么 L5 才调模型？** A：前三档都是本地操作零成本，能本地解决就不花模型的钱；占用到 0.95 说明本地手段已尽。
- **Q：979 token/轮怎么算的？** A：1958 字符 × 2 字符/token 的粗估；按文档 3 字符/token 口径约 650，都是估算，不是 tokenizer 精确值。
- **Q：为什么不全部并发？** A：写操作和顺序依赖会破坏正确性；只并相邻只读是最保守的安全线。
- **Q：缓存断点为什么打两个？** A：system 整段不变永远可命中；消息列表末尾的断点让"上一轮的全部对话"在新一轮里命中缓存。
