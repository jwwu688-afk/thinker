# 上下文窗口压缩策略：剪中间 / 折叠工具结果 / 只读投影 / 模型摘要

> 背景：上下文窗口有上限，且「装得越满、越靠近中间的内容模型越记不住」（Lost in the Middle / context rot）。所以工程上不是「塞更多」，而是**只保留最小的高信号 token 集合**。本文讲四种常用压缩策略，各自解决不同的问题。

---

## 0. 四种策略一句话总览

| 策略 | 干什么 | 是否丢信息 | 谁来执行 | 典型触发时机 |
|------|--------|-----------|---------|-------------|
| **剪中间** | 长内容只留头尾，中间掐掉并标注 | 有损（但标注了被剪数量） | 确定性的规则，不调模型 | 单条内容（文件/日志）过长时 |
| **折叠工具结果** | 清掉不再需要的旧工具调用/结果 | 有损（旧结果被清） | 规则或平台能力 | 接近窗口上限、结果已过期时 |
| **只读投影** | 保留完整历史，另生成一份精简视图喂给模型 | 无损（原件在，视图可重算） | 规则生成投影 | 每轮/定期 |
| **模型摘要** | 用 LLM 把旧历史压缩成结构化状态块 | 有损（靠模型提炼） | 调 LLM | 达到阈值或手动触发 |

核心取舍贯穿始终：**前三个尽量「规则化、可逆、可重算」，最后一个才动用模型，因为模型摘要有损且要花钱/耗时间。**

---

## 1. 剪中间（Truncate the Middle / Head-and-Tail）

### 是什么

一条内容（一个大文件、一段日志、一个长 JSON）太长时，**保留开头和结尾，把中间掐掉，换成一行明确的数量标记**，而不是从尾部硬截断。

### 为什么这么剪

模型对「开头」和「结尾」的注意力最高，对「中间」最差（Lost in the Middle 效应）。所以丢中间比丢结尾代价更小——文件的关键信息往往在头（imports、类声明、字段定义）和尾（导出、最近的改动、报错位置）。

### 典型做法

- **读文件**：超过预算（如 40 行）时，保留前 N 行 + 后 N 行，中间替换成 `…（中间省略 X 行，可用 grep/指定行号再读）…`。
- **JSON 大数组**：保留前 2 个对象 + 结构 schema + 被省略的数量说明，删掉其余同类对象——结构信息不丢，重复数据丢 95%。
- **命令输出/日志**：扫错误关键词，有错就围绕报错取「前 5 行 + 后 15 行」的聚焦窗口；没错就只给头尾摘要。

### 关键点

- **确定性规则，不调模型**，零额外成本、零延迟。
- **必须标注被剪了多少**（「省略了 1200 行」），否则模型会把「看不到的部分」脑补成「不存在」。
- 要给模型留「再取中间」的入口（指定行号 / grep），做到按需取回。

## 2. 折叠工具结果（Folding / Clearing Tool Results）

### 是什么

Agent 跑久了，历史里堆满工具调用和它们的返回结果（读过的文件、跑过的命令、搜过的结果）。其中绝大多数**在几步之后就没用了**，却一直占着窗口。折叠就是把这类「已经消费过的旧工具结果」从上下文里清掉。

### 为什么是「最安全、最轻量」的压缩

这是 Anthropic 官方点名的「最轻、最安全的压缩手段」之一，理由很直白：**工具一旦被调用过、结果已经被模型读进过一次，后续回合通常不再需要看它的原始返回**。清掉旧结果几乎不伤当前任务，却能立刻腾出大量空间。

### 两种形态

1. **规则式清空**：把旧工具结果替换成占位符，如 `[tool result cleared; re-run if needed]`。
2. **平台原生「context editing」**：Anthropic 在 Claude Developer Platform 上提供了 context editing，接近窗口上限时**自动**清掉过期的工具调用和结果，同时保留对话流。

### 关键点

- **别拆散工具对**：工具调用（tool-use）和它的结果（tool-result）要一起清，不能只清一半，否则模型看到「调用没结果」会乱。
- 实测收益明显：Anthropic 在 100 轮 web 搜索评测里，context editing 让原本会因窗口耗尽而失败的流程跑通，**token 消耗下降 84%**；配合 memory tool 性能提升 39%。
- **旧结果先清，别急着摘要**——清空是「无损于当前任务」的操作，比模型摘要有把握得多。

## 3. 只读投影（Read-Only Projection / 折叠日志）

### 是什么

**完整历史（真相）保留一份不动**，另生成一份「精简视图（投影）」喂给模型的 API 请求。模型只看到投影，但完整内容始终存在，随时可还原、可追溯。

### 为什么叫「只读」

关键在「投影是只读的、可重算的」：真相不因压缩而丢，投影每一轮都能重新生成。这解决了纯「删除式压缩」最大的痛点——一旦删错就找不回来。

### 典型做法

- **UI 保留完整历史**（用户能看到、能回滚），**API 只发投影视图**。
- 维护一个**只追加的「折叠日志」**（append-only collapse log），记录每一步折叠了什么；每轮据此重新生成一份精简投影发给模型。
- 被折叠掉的消息在投影里以摘要或占位出现，但完整内容在本地/UI 仍在。

### 关键点

- **无损、可逆、可审计**：原始内容永在，投影只是「当前这轮给模型看的快照」。
- 需要同步维护「释放了多少 token」的计数，让下游逻辑知道窗口真实还剩多少。
- 适合「既要省 token、又绝不允许丢信息」的场景（如用户可见的聊天历史）。

## 4. 模型摘要（Model Summarization / Compaction）

### 是什么

用 LLM 把较早的对话历史**压缩成一段结构化的状态块**，用摘要替换原始历史，从而把窗口腾出来。这是四者里唯一「调用模型、有损」的手段。

### 为什么是「最后手段」

摘要本质是「让模型自己决定什么重要、什么可以丢」，是有损的、要花钱花时间的，还可能漏掉关键约束。所以正确的顺序是：**能清空（策略 2）就别删、能投影（策略 3）就别摘要，实在不行才上模型摘要**。

### 典型做法

- **结构化摘要，而不是自由散文**：让模型往固定字段里填——「目标 / 已完成的里程碑 / 待办 / 用户约束 / 已改动的文件 / 未解决的错误」，比一句「总结这段对话」可靠得多，因为字段清单是模型无法悄悄跳过的 checklist。
- **保底规则**：保留最近的 4~8 轮原文，只摘要更早的部分；用户明确约束、未解决的报错、已定决策要优先保留。
- **配熔断**：摘要失败重试、失败就退化为「丢最旧的一批直到塞得下」，连续失败就熔断，避免死循环。
- **可逆**：原始历史归档到冷存储，摘要可审计、可回看。

### 各家形态

- **Anthropic Compaction**：服务端替你把旧轮次换成摘要，你无需自己写摘要代码；支持「按需触发」和「达到 token 阈值自动触发」两种。
- **Claude Code `/compact`**：接近上限时自动压缩，保留代码模式、文件状态、关键决策；可 `/compact 聚焦于 API 改动` 指定重点，或 `/rewind` 后「从这里起摘要 / 到这里为止摘要」只压一部分。

### 关键点

- **朝 schema 摘要，不朝自由散文**。
- **原文归档**，让压缩可逆、可审计。
- 一句话定调：**「压缩，而不是截断」**——从尾部硬砍会丢掉「解释当前状态的那些决策」，摘要要把仍生效的决策和约束提炼出来。

## 5. 四者怎么选：一张决策表

| 场景 | 首选策略 | 理由 |
|------|---------|------|
| 单条文件/日志/JSON 太长 | **剪中间** | 规则化、零成本，丢的是注意力最低的中间 |
| 跑久了堆满旧工具结果 | **折叠工具结果** | 最轻最安全，旧结果当前任务基本用不上 |
| 既要省 token 又绝不能丢历史 | **只读投影** | 无损、可逆、可审计 |
| 历史太长，必须提炼「决策/约束/待办」 | **模型摘要** | 唯一能理解语义并压缩的手段，但有损 |

**通用优先级：剪中间 / 折叠（规则、快、便宜）→ 只读投影（无损）→ 模型摘要（有损、花钱，兜底）。**

---

## 6. 关键提醒（一句话版）

1. 窗口是「预算」，不是「越大越好」——中间内容注意力最差，塞满反而更糟。
2. 工具结果是窗口膨胀的头号来源，能清就清，别让旧结果堆着。
3. 压缩**能规则化就别调模型**；必须调模型就**朝结构化 schema 摘要**。
4. 无论哪种压缩，**原文归档、可逆可审计**是底线，别做不可逆的硬删除。
