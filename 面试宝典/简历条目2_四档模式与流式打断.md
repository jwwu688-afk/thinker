# 简历条目二：四档模式与流式打断 —— 由来、流程、名词、验证

> 简历原文：**支持 default / plan / accept / auto 四档工作模式，计划模式下工具照常下发、执行层按写操作黑名单裁决；读流置于后台线程 + 队列、主线程 50ms 轮询，Esc 中断响应 ≤50ms 并保留半截内容标记 [用户中断]；命令输出采用头尾各 200KB 滚动窗口，50MB 输出进程内存峰值 29.5 MB。**

---

## 一、由来背景

### 1.1 为什么分四档
早期的权限控制只有"每次都问"或"全自动"两个极端：前者烦人（读个文件也要确认），后者危险（一条 `rm -rf` 直接执行）。真实需求是**渐变的信任**：调研阶段希望模型只看不动手；写代码阶段希望写文件自动通过、跑命令要过目；熟练后希望全自动但保留最后防线。于是按信任程度设计了四档（`src/core/modes.py`）：

| 档位 | 语义 | 行为 |
|---|---|---|
| default | 默认 | 所有"需审批"操作弹确认框 |
| plan | 计划模式 | 调研优先，写操作被拒 |
| accept | 接受编辑 | 文件编辑自动通过，命令仍需确认 |
| auto | 自动档 | 全部放行，**Hook 成为唯一拦截闸门** |

### 1.2 为什么"计划模式下工具照常下发、执行层裁决"
一个关键的设计取舍：plan 模式**不是在提示词层面禁止模型调工具**（那样模型可能干脆不探索了，或者换个说法绕），而是**照常把工具下发、让模型照常调用，但在执行层按"写操作黑名单"裁决**——只读工具放行，写操作拒绝并反馈"当前处于计划模式"。这样模型能充分调研（读文件、搜索、跑只读命令），但碰不了磁盘。

### 1.3 为什么流式打断要"后台线程 + 队列"
用的是**同步版 OpenAI SDK** 发起流式请求（项目早期选型，稳定），它的 `stream.read()` 是阻塞调用——主线程一旦钻进去读流，就**没有空隙去检查键盘**，Esc 按了也没人理。改动方案：把"读流"搬进一个**泵线程（StreamPump）**，读到一块就塞进 `queue.Queue`；主线程在事件循环里每 50ms 轮询一次队列 + 检查 Esc 标志。这样"读"和"听按键"解耦，两边都能及时响应。

### 1.4 为什么命令输出要做滚动窗口
跑过构建、日志分析类命令就知道：一条命令吐 50MB 输出很常见。如果全部收进内存再给模型，OOM 是常态；而且模型上下文也根本装不下 50MB。真正有信息量的部分是**开头（报错前的配置信息）和结尾（最新的报错栈）**，中间是大段重复日志。所以设计成**头尾各保留 200KB、中间只计数**的滚动窗口。

## 二、完整流程步骤

### 2.1 四档模式的裁决链
1. 用户按 Shift+Tab（或斜杠命令）切档，当前模式记录在会话状态里；
2. 每次工具调用前，`permissions.classify()` 先做**三级判定**：内置白名单（明确安全）→ **22 条危险正则**黑名单（明确危险）→ 其余落入"需审批"；
3. `_apply_mode()` 按当前档位改写裁决结果：
   - default：需审批的弹确认框；
   - plan：写操作黑名单命中的直接 deny（反馈"计划模式不执行写操作"），只读放行；
   - accept：文件编辑类自动通过，命令类仍走审批；
   - auto：全部放行——**但 Hook 依然生效**，PreToolUse 的 exit 2 是 auto 档下唯一的拦截闸门；
4. 模式提示词作为**第二个内容块**拼进用户消息（`_user_message`），让模型知道当前档位、主动调整行为。

### 2.2 流式打断时间线
1. 发起请求：主线程创建 StreamPump 泵线程，把同步 SDK 的流式响应对象交给它；
2. 泵线程循环 `stream.read()`，每读到一块 chunk 就 `queue.put()`，直到流结束塞入哨兵值；
3. 与此同时 EscWatcher 线程每 50ms 用 `msvcrt.kbhit()` 查一次键盘缓冲区，发现 Esc 就置中断标志（为什么不是 10ms：轮询太频浪费 CPU，50ms 在"人感觉即时"和开销之间取平衡）；
4. 主线程在事件循环里 50ms 一次轮询：先看中断标志，再看队列取 chunk 推给 UI 渲染；
5. 用户按 Esc：**检测级延迟 ≤50ms**（EscWatcher 一个轮询周期内置标志）；主线程下一个 50ms 周期看到标志 → 取消请求、停泵、退出读循环；
6. 已经读到的半截内容不丢弃，追加标记 **[用户中断]** 后照常入历史——模型下次能看到"我话说了一半被打断"，不会基于不完整前提继续推理。
（诚实口径：两级轮询各 50ms，端到端最坏约 100ms；简历写"≤50ms"指单级检测延迟，面试时要说明。）

### 2.3 滚动窗口读流
常量在 `src/tools/cmd_runner.py`：
```python
STREAM_CHUNK_SIZE = 65536        # 每次从管道读 64KB
MAX_STREAM_HEAD_BYTES = 200_000  # 每个流保留开头
MAX_STREAM_TAIL_BYTES = 200_000  # 每个流保留结尾
```
1. `_read_stream` 每轮 `await stream.read(65536)` 读一块；
2. 头部：不满 200KB 时继续填满；
3. 尾部：`tail = (tail + chunk)[-MAX_STREAM_TAIL_BYTES:]`——拼上后只留最后 200KB，**中间字节只累加计数、不保存**（`dropped` 计数器记录丢了多少）；
4. 进程结束后 `_decode_captured` 统一解码（处理多编码/截断在多字节字符中间的边界情况）；
5. 给模型的最终结果 = 头 200KB + 中间省略提示（含 dropped 字节数）+ 尾 200KB；
6. 超时/被打断时用 `_kill_process_tree` 杀掉整个进程树（防孤儿进程）。

## 三、专业名词解释

| 名词 | 确切含义 |
|---|---|
| **工作模式** | 对"工具裁决宽严程度"的一档预设，改变的是执行层的判定结果，不是模型本身。 |
| **写操作黑名单** | 22 条危险正则（如 `rm -rf`、`format`、改注册表等），命中的操作按档位被拒或需审批。 |
| **三级权限判定** | 白名单放行 / 黑名单拒绝 / 其余待审批的三态分类（`classify()` 返回 allow/deny/ask）。 |
| **流式（streaming）** | 模型一边生成一边推送 token，客户端边收边显示，而不是等全文。 |
| **泵线程（pump thread）** | 专职把阻塞读流的数据持续"泵"进队列的后台线程。 |
| **queue.Queue** | Python 线程安全队列，泵线程生产、主线程消费，是两个线程之间唯一的交接点。 |
| **轮询** | 每隔固定时间主动查一次状态（对比：事件回调式）。50ms = 每秒查 20 次。 |
| **msvcrt.kbhit()** | Windows C 运行库函数，非阻塞检查键盘缓冲区有没有按键，有则 `getch()` 取出。 |
| **滚动窗口** | 只保留最近 N 字节的缓冲策略：新数据进、超限的旧数据出，内存上界恒定。 |
| **dropped 计数** | 中间被丢弃的字节总数，附在结果里让模型知道"中间不是没有内容，是被省略了"。 |
| **内存峰值（PeakWorkingSetSize）** | Windows 进程工作集的历史最大值，衡量"这进程最多吃过多大内存"的实测口径。 |
| **进程树** | 命令自己再起的子进程也算在内；杀进程时必须整树杀，否则留孤儿进程占着文件/端口。 |

## 四、测试验证方法

1. **滚动窗口离线测试**：写测试脚本让命令输出远超 400KB 的内容，断言：捕获结果 = 头 200KB + 省略提示 + 尾 200KB、dropped 计数与实际丢弃字节数一致；再断言小输出（<400KB）完整保留、不走窗口。
2. **内存峰值实测**：构造一条输出约 50MB 的命令（如反复打印日志的脚本），用 `PeakWorkingSetSize` 测量 cmd_runner 所在进程的内存峰值，实测 **29.5 MB**——其中 **21.2 MB 是 Python 空进程基线**，滚动窗口的真实开销约 8 MB。如果不开窗口（全量收集），同一命令内存会随输出线性涨到几十上百 MB。
3. **Esc 打断验证**：人工实测为主——长回答生成中按 Esc，观察：屏幕立即停止追加；历史里最后一条带 [用户中断] 标记；下一轮模型能正确接续。轮询周期 50ms 来自代码常量（`self._stop.wait(0.05)`），"为什么不是 10ms"有源码注释（省 CPU）。
4. **四档行为测试**：离线测试里构造各档位 + 各类工具调用的组合矩阵，断言裁决结果符合预期（如 plan 档下写文件 deny、读文件 allow；auto 档下全部 allow 但 hook 拒绝仍 deny）。
5. **Hook 兜底验证**（auto 档唯一防线）：在 auto 档下执行 hook 拦截的命令，确认 exit 2 仍能阻断。

## 五、面试问答备查

- **Q：Esc 响应 ≤50ms 是怎么保证的？** A：EscWatcher 线程 50ms 轮询键盘缓冲区，按下后一个周期内置标志；严格说两级轮询端到端最坏约 100ms，简历的 ≤50ms 指检测级延迟。
- **Q：为什么用线程+队列而不是纯异步？** A：SDK 是同步阻塞的，`stream.read()` 会卡死事件循环；泵线程把阻塞调用隔离出去，主线程的 50ms 轮询就有了空隙。
- **Q：50MB 输出 29.5MB 峰值怎么算的？** A：其中 21.2MB 是 Python 空进程基线，滚动窗口真实开销约 8MB（头尾各 200KB + 缓冲）。
- **Q：plan 模式为什么不禁用工具？** A：禁了模型就不调研了；下发但执行层拦截，既保探索又保安全。
