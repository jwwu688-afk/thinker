# 简历条目四：记忆、会话持久化与存档治理 —— 由来、流程、名词、验证

> 简历原文：**THINKER.md 全文注入 + MEMORY.md 只注入索引、支持整行 @路径 导入；消息逐条落盘 JSONL，/resume 恢复；压缩结果以 compaction 行落盘，resume 按 keep_from 把原始记录重建为有效消息；/clean 采用临时文件 + 原子替换归档（gzip 后 8%~15%，不丢失原始记录）。**

---

## 一、由来背景

### 1.1 为什么记忆要"全文 + 索引"两级
项目有两类长期记忆文件，膨胀风险完全不同：

- **THINKER.md**（项目约定，类似 CLAUDE.md）：内容是用户手写的项目规范，体量可控，而且**每一条都可能影响行为正确性**——漏一条就可能违反约定，所以**全文注入**系统提示词。
- **MEMORY.md**（跨会话长期记忆）：如果也全文注入，随着记忆积累会无限膨胀、每轮烧 token。所以**只注入索引**（每条记忆的标题/一行摘要），模型看到索引后认为相关，再通过 @导入或读文件取全文。

### 1.2 为什么支持 @路径 导入
有些内容天然是模块化的（规范文档、术语表、常用代码约定），不该全堆在 THINKER.md 里。@导入让主文件像"目录"一样引用外部文件：**整行以 @ 开头 + 路径**才展开，行中间提到 @ 不误伤。随之而来的是三个必须防的坑：循环导入（A 导 B、B 导 A）、层数失控（导入链无限深）、路径歧义（相对谁？）——对应四道保护。

### 1.3 为什么消息要逐条落盘 JSONL
早期版本如果进程崩溃 / 终端误关，整轮会话全丢。逐条落盘（**JSONL**，每行一条 JSON）意味着：每产生一条消息（用户输入 / 模型回复 / 工具结果）立刻追加写文件。崩溃最多丢"正在写的半条"，之前的全部还在。这也是 /resume 的基础。

### 1.4 为什么压缩结果也要落盘
如果压缩只改内存，重启后 /resume 恢复的还是原始的长历史——压缩白做。所以引入 **compaction 行**：压缩动作本身作为一条特殊记录写进会话文件（记录"从哪压到哪、摘要是什么"）。resume 时遇到 compaction 行，按 **keep_from** 指针把原始记录**重建为有效消息**——原始记录不丢（可追溯），但有效上下文变成压缩后的精简版。

### 1.5 为什么 /clean 要"临时文件 + 原子替换"
清理会话文件时如果直接原地删改，写到一半断电/崩溃，文件就毁了。所以流程是：先把要保留的内容写到**临时文件**，全部写完并通过检查后，用 `os.replace` 做**原子替换**（操作系统保证：要么旧文件完好、要么新文件完整生效，不存在中间态）。旧内容同时 gzip 归档，**原始记录不丢失**。

## 二、完整流程步骤

### 2.1 记忆注入与 @导入
1. 启动时读全局 `~/.thinker/THINKER.md`（项目级 `.thinker/THINKER.md` 叠加），**全文**进入系统提示词；
2. `MEMORY.md` 只解析出记忆条目**索引**注入（一行一条摘要），全文不进；
3. 主文件里逐行扫 `_IMPORT_RE = re.compile(r"^\s*@([^\s#]+)\s*$")`——只有**整行**是 `@路径`（允许首尾空白，`#` 注释豁免）才展开；行中间出现 @ 原样保留；
4. 四道保护：
   - **seen 集合防循环**：导入过的文件不再展开（A→B→A 直接剪断）；
   - **MAX_IMPORT_DEPTH = 3**：嵌套超过 3 层，@行原样留着不展开；
   - **相对路径基准**：相对**记忆文件所在目录**解析，不是相对进程 cwd（否则从别的目录启动 thinker 路径全错）；
   - 文件不存在则保留原行并给提示，不静默吞掉。
5. 注意口径：@导入是 **THINKER.md 的能力**，MEMORY.md 后面挂 @ 不生效——面试别说混。

### 2.2 会话持久化与 /resume
1. 会话运行中，每条消息（user / assistant / tool）产生即**追加写入**会话 JSONL 文件（`src/core/session.py`）；
2. 用户开新会话或退出后，旧会话文件留在磁盘上，带会话元信息（时间、模型、轮次）；
3. `/resume` 列出历史会话供选择 → 逐行读 JSONL → 还原 `messages_history` → 接着聊。

### 2.3 compaction 行与 keep_from 重建
1. 压缩发生时（五档里的 L5），生成摘要 + 压缩边界信息；
2. `append_compaction` 把压缩事件**作为一条记录**追加进会话 JSONL：含 keep_from 指针（"有效消息从第 N 条开始"）与摘要内容；
3. **原始消息行一条不删**，仍留在文件里；
4. `/resume` 重放文件时，遇到 compaction 行执行 `_apply_compaction`：第 N 条之前的原始记录被"逻辑跳过"，**重建为压缩后的有效消息列表**；
5. 实测案例：某长会话有效消息 **805 条 → 14 条**，上下文占用从 **179.8%**（已超窗，靠压缩续命）压回 **<70%**——且想翻旧账时原始记录还在，可完整追溯。

### 2.4 /clean 的原子归档
1. 用户执行 `/clean`，要清理的是"tmp 工作残留 + 会话文件瘦身"；
2. 程序先把**要保留的内容**写入临时文件（`*.tmp`），写完做完整性检查；
3. `os.replace(tmp, target)` 原子替换——Windows/Linux 语义都保证不出现"半新半旧"的文件；
4. 被替换下来的旧内容 gzip 压缩归档保留，**不丢失原始记录**；
5. 压缩比实测：**18.5% ~ 49%**（即 gzip 后占原来的 18.5%~49%）——简历里写的"8%~15%"来自早期一次乐观测量，面试按实测口径答。

## 三、专业名词解释

| 名词 | 确切含义 |
|---|---|
| **全文注入** | 文件完整内容放进系统提示词，每轮都随请求发送。 |
| **索引注入** | 只注入每条记忆的一行摘要，全文按需再取，控制常驻 token。 |
| **@导入** | 以 `@路径` 整行引用外部文件，加载时把文件内容展开进上下文。 |
| **循环导入** | A 导入 B、B 又导入 A，不防护会无限递归；用 seen 集合剪断。 |
| **JSONL** | JSON Lines：每行一条独立 JSON 对象的文本格式，追加写友好、逐行解析可容错。 |
| **/resume** | 从落盘的会话文件恢复历史对话继续工作的命令。 |
| **compaction 行** | 会话文件里记录"一次压缩事件"的特殊行（keep_from 指针 + 摘要），原始消息不删。 |
| **keep_from** | 指针：有效上下文从第 N 条消息开始重建，之前的记录逻辑跳过但物理保留。 |
| **有效消息** | resume 重建后实际进入模型上下文的消息集合（压缩后的精简版）。 |
| **临时文件 + 原子替换** | 先写 tmp 再 `os.replace` 的写盘模式，保证任意时刻崩溃文件都处于完整状态。 |
| **os.replace** | 操作系统级原子替换文件的调用：同分区下替换是不可分割的操作。 |
| **gzip 归档** | 用 gzip 压缩旧数据存档，省空间且保留完整原始记录。 |
| **占用率 179.8%** | 会话累积超过模型窗口上限的比例；靠压缩把有效上下文拉回窗口内继续会话。 |

## 四、测试验证方法

1. **@导入离线测试**：构造含 @行的记忆文件，逐项断言：整行 @ 展开成功；行中间 @ 不展开；`#` 注释行豁免；A↔B 循环导入被 seen 剪断；4 层嵌套在第 3 层停止；从不同工作目录启动，相对路径解析结果一致（相对记忆文件目录而非 cwd）。
2. **落盘与 resume 测试**：跑一段会话后 kill 进程，重启 `/resume`，逐条比对恢复的 `messages_history` 与落盘 JSONL 内容一致；再断言"每条消息产生后立即追加写"（落盘时序）。
3. **compaction 重建测试**：构造带 compaction 行的会话文件，`/resume` 后断言：有效消息 = 压缩后精简版；原始记录仍完整存在于文件中（打开 JSONL 逐行核对）。真实案例数据：805→14 条、179.8%→<70%。
4. **/clean 原子性验证**：正常路径——替换后文件内容与预期一致、归档可解压还原；异常路径——人为在写入中途中断，断言目标文件仍是旧版完整内容（没有半截文件）。压缩比用真实会话文件 gzip 前后字节数实测：18.5%~49%。
5. **不丢数据验证**：/clean 归档解压后与清理前的原始记录逐行比对一致。

## 五、面试问答备查

- **Q：为什么 THINKER.md 全文注入而 MEMORY.md 只给索引？** A：前者是行为正确性约束、体量可控；后者会无限膨胀，索引注入 + 按需取全文控制常驻成本。
- **Q：@导入有哪些防护？** A：四道——seen 防循环、深度上限 3、相对记忆文件所在目录解析、不存在的路径不静默吞。
- **Q：压缩后原始消息还在吗？** A：在。compaction 行只是加了一条"从 keep_from 开始重建"的记录，原始行物理保留、逻辑跳过，随时可追溯。
- **Q：/clean 会不会丢数据？** A：不会。tmp + os.replace 保证原子性，旧内容 gzip 归档保留；实测压缩比 18.5%~49%（简历 8%~15% 偏乐观，面试按实测答）。
