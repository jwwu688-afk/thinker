# 简历条目一：单层架构与扩展机制 —— 由来、流程、名词、验证

> 简历原文：**单层主循环驱动，工具/命令一行注册、技能放 SKILL.md 加载；task 派活给 4 种内置子 agent，翻页隔离上下文、只回传结论；提供两事件生命周期 Hook 与 MCP 外部工具接入，分别由 settings.json / mcp.json 配置。**

---

## 一、由来背景（为什么这么设计）

### 1.1 为什么要"单层主循环"
项目最早一版的主循环是**递归写法**：一轮对话结束后，函数在末尾 `return await self._run_one_iteration()` 调自己。这样写直观，但有两个致命问题：

1. **Python 有递归深度上限（默认 1000 层）**。一个长会话跑几百轮，每轮递归一层，迟早撞上 `RecursionError`，会话直接崩。
2. **每轮递归都压栈**，栈帧里残留着上一轮的局部变量引用，长会话内存只增不减。

所以重构成了**单层 while 循环**（`src/core/conversation.py:971` 附近）：

```python
while True:
    should_continue = await self._run_one_iteration()
    if not should_continue:
        break
```

一轮 = 一次函数调用，函数返回就出栈，栈深度恒定为 1，跑一万轮也不会递归爆栈。"该不该继续"变成返回值，退出条件显式化。

### 1.2 为什么要"一行注册"
工具和斜杠命令如果靠 if/else 硬编码分发，每加一个功能要改三处（分发逻辑、schema 清单、文档），容易漏。所以改成**注册表模式**：每个工具文件自带类定义 + schema，往注册表里 append 一行就完成接入，模型看到的工具清单由注册表自动生成，分发也查同一张表。**新增成本 = 一个文件 + 一行**。

### 1.3 为什么技能要放 SKILL.md
技能本质是"按需加载的说明书"。如果全部塞进系统提示词，token 成本爆炸；如果模型根本不知道有这个技能，又永远不会去加载。折中方案是**三层渐进披露**：

- 第一层：技能**清单**（名字 + 一句话描述）常驻系统提示词，让模型知道"有什么"；
- 第二层：模型决定用时，读 SKILL.md 的 frontmatter/描述拿调用方式；
- 第三层：真正需要细节时才读**正文**（截断上限 20000 字符）。

### 1.4 为什么要有子 agent
主对话的上下文是"寸土寸金"的：大范围搜索代码、出方案、做审查这类任务，中间过程会产生海量文本，直接在主对话里做会迅速撑爆上下文。所以把这类活派给**子 agent**：它在自己独立的上下文里干脏活，干完只把结论带回来。

### 1.5 为什么要有 Hook 和 MCP
- 有些逻辑不该写死在代码里（比如"每次会话开始注入 git status"、"执行前拦 rm -rf"），不同用户需求不同，所以做成**生命周期 Hook**，让用户用脚本挂载。
- 外部世界的能力（数据库、浏览器、企业内部系统）不可能全部内置，所以接 **MCP（Model Context Protocol）**，外部工具按标准协议接入，配置即用。

## 二、完整流程步骤

### 2.1 单层主循环的一轮（一次 iteration）
1. `_read_user_input()`：读用户输入。**斜杠命令在这里被拦截**——如果输入以 `/` 开头且命中命令表，直接本地执行（不发给模型），执行完进入下一轮；
2. 普通输入则构造消息、发模型请求（异步 `await`，等待期间主循环不阻塞事件循环）；
3. 模型返回工具调用 → `_handle_tool_calls()`：顺序为 **Hook 预检 → 权限 classify/deny → 用户审批 → 实际执行**；
4. 工具结果回填消息历史，`update_token_usage` 更新占用率；
5. 函数返回 `True`，`while` 进入下一轮。**没有任何递归**。

### 2.2 工具/命令一行注册
- 工具：在 `src/tools/` 下定义工具类（含 `name`、`json_schema()`、`execute()`），在注册表里加一行 `ToolX()`；运行时模型看到的工具清单、分发执行都查这张表。
- 斜杠命令：同理，命令名 + 处理函数注册一行，`_read_user_input` 拦截后查表执行。

### 2.3 技能加载（SKILL.md）
1. 启动时 `skill_manager` 扫描两个目录：全局 `~/.thinker/skills/`、项目级 `.thinker/skills/`，解析每个 SKILL.md 的 frontmatter；
2. `available_block()` 生成技能清单（实测 **1,958 字符**），随系统提示词常驻——注意是**全文注入清单**，不是检索式注入；
3. 模型要调技能 → 工具清单里有一个 skill 工具（`skill_tool.json_schema()`）；
4. 模型点名某技能 → 读正文，超过 `MAX_SKILL_BODY_CHARS = 20000` 字符则截断并附提示。

### 2.4 task 派活给 4 种内置子 agent
4 种子 agent 注册在 `src/tools/subagent/builtin_agents.py` 的 `BUILTIN_AGENTS` 元组里，由 `SubagentManager` 单例的字典统一管理：

| 子 agent | 定位 | 权限 |
|---|---|---|
| general-purpose | 兜底 | 唯一有写权限 + 命令权限 |
| explore | 只读定位（"这东西在哪"） | 只读 |
| plan | 只读调研 + 出方案（"该怎么改"） | 只读 |
| code-reviewer | 只读审查（"哪里有问题"） | 只读 |

流程：
1. 主 agent 发 `task` 工具调用，指定子 agent 类型和任务描述；
2. `start_task()` 创建子 agent，它有**自己独立的 `messages_history`**——和主对话一样的 `[[]]` 二维翻页结构，但互不可见（这就是"翻页隔离上下文"）；
3. 子 agent 独立跑完它的多轮循环；
4. **只有最终结论文本回传给主 agent**，中间的搜索、读文件、试错全部留在子 agent 上下文里，不污染主对话。
5. 主 agent 同步等待子 agent（主 agent 此时不接新输入），但界面靠心跳不冻结。

### 2.5 两事件生命周期 Hook
机制支持 4 个事件（`hooks.py`: `SUPPORTED_EVENTS = ("SessionStart", "PreToolUse", "PostToolUse", "SessionEnd")`），**我实际配置了 2 个**（SessionStart 注入环境信息 + PreToolUse 拦截）——面试口径要说清："机制支持 4 个，我实际用了 2 个"。

流程（以 PreToolUse 为例）：
1. 配置写在**用户级** `~/.thinker/settings.json`，启动时加载一次；
2. 会话中每次工具调用前，`HookRunner.run_event("PreToolUse", payload, tool_name=...)` 被调用；
3. 按 `matcher` 正则筛选适用的 hook（空 = 匹配全部），用 `subprocess` 起脚本、带超时 `wait_for` 等待；
4. **exit 0** = 放行（stdout 可注入上下文）；**exit 2** = 阻断，工具不执行，stderr 反馈给模型；
5. 输出截断保护：4000 字符（注入类）/1000 字符（反馈类），失败提示节流最多 3 次防刷屏；
6. 时序上 PreToolUse 在**权限确认之前**串行执行——hook 说不行，连审批框都不会弹。

### 2.6 MCP 外部工具接入
外部工具服务器在 `~/.thinker/mcp.json` 配置（command/args 或 url），启动时拉起、把外部工具并入工具注册表，模型用起来和内置工具无异。

## 三、专业名词解释

| 名词 | 确切含义 |
|---|---|
| **主循环（main loop）** | Agent 的驱动骨架：读输入→调模型→执行工具→回填结果，周而复始。单层 = 用 while 迭代而非函数递归实现。 |
| **递归深度上限** | Python 默认调用栈约 1000 层，递归实现的主循环长会话会撞 `RecursionError`。 |
| **事件循环 / await** | asyncio 的调度器；`await` 处让出控制权，等待 I/O 时 CPU 可以去干别的（如轮询按键）。 |
| **注册表模式** | 用一张表（dict/list）集中管理"名字→实现"的映射，新增能力只需注册一行，不改分发逻辑。 |
| **schema** | 描述工具"叫什么、参数长什么样"的 JSON 结构，模型据此知道怎么调用工具。 |
| **渐进披露** | 信息分三层给：先给清单（便宜），再给用法，最后给正文（贵），控制 token 成本。 |
| **子 agent** | 拥有独立上下文和独立消息历史的辅助 agent，由主 agent 通过 task 工具派活。 |
| **上下文隔离** | 子 agent 的中间过程对主 agent 不可见，只有结论回传，防止大段中间文本挤占主上下文。 |
| **生命周期 Hook** | 在会话关键节点（开始/工具前/工具后/结束）执行用户自定义脚本的机制。 |
| **exit code 协议** | 约定：脚本退出码 0 = 放行，2 = 阻断。模型与用户脚本之间零耦合的通信方式。 |
| **MCP** | Model Context Protocol，Anthropic 提出的标准协议，让外部工具/数据源以统一方式接入 AI 应用。 |
| **matcher** | hook 配置里的正则，决定这个 hook 只对哪些工具名生效。 |

## 四、测试验证方法

1. **离线单测**：项目测试目录有 31 个纯离线断言测试（不调模型接口、不花钱），覆盖工具注册、命令分发、技能清单生成等。技能正文截断（20000 字符）有专门断言：构造超长 SKILL.md，验证截断提示文案。
2. **主循环行为验证**：通过模拟多轮输入（不真调模型），断言 `messages_history` 的轮次结构与栈深恒定；递归版 vs 循环版的长会话对比可在本地复现 RecursionError。
3. **子 agent 隔离验证**：构造一个子 agent 任务（如让它搜索多个文件），跑完后检查主对话 `messages_history` 中**只出现了结论文本**，子 agent 的中间调用记录不在主历史里。
4. **Hook 验证**：写一个测试 hook（echo 脚本 + 一个 `exit 2` 的拦截脚本），分别验证放行/阻断两条路径、stdout 截断、超时行为； PreToolUse 阻断时确认审批框不弹、模型收到拒绝反馈。
5. **实际会话验证**：日常使用中即验证——每轮 token 用量统计里能看到技能清单常驻的 1,958 字符（约 979 token/轮，按 2 字符/token 估算口径）。

## 五、面试问答备查

- **Q：为什么不用递归？** A：Python 1000 层递归上限 + 栈帧残留导致内存不降；while 循环栈深恒为 1，退出条件显式。
- **Q：加一个新工具要改几处？** A：一个文件 + 注册表一行，schema 与分发自动生效。
- **Q：子 agent 阻塞主 agent 吗？** A：逻辑上同步等待（主 agent 不接新输入），但事件循环没有被卡死，界面靠心跳保持响应。
- **Q：Hook 支持几个事件？** A：机制支持 4 个（SessionStart/PreToolUse/PostToolUse/SessionEnd），我实际配置了 2 个。
